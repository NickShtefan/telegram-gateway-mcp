Telegram MCP-шлюз

Один демон держит сессию отдельного Telegram-аккаунта и отдаёт её любому агенту как набор MCP-инструментов. Схема собрана под четыре задачи: цены в барахолке, сводка по каналу, ответы на новые посты и переписка с человеком до договорённости. Для двух последних шлюз работает и без агента: сам замечает события и запускает агента. Ядро почти целиком берётся из channel-scope и helper.

Кейсы

Первые две задачи агент решает сам за один разговор. Две другие постоянные: шлюз должен работать, пока агент не запущен, ловить новые посты и ответы собеседника и будить агента. Мониторинг реагирует на событие и забывает его, а переписка помнит цель и всё, что уже сказано.

разовый запрос

Цены в барахолке

«Зайди в чат барахолки, найди объявления на такую-то тему и дай аналитику по ценам»

tg_resolve → tg_list_topics → tg_search_chat → tg_export (photos=thumb) → код агента → tg_get_media

Что нужно шлюзу

  • Темы форумов: барахолки часто разбиты на «Продам», «Куплю», «Обмен».
  • Выгрузка в файл: сотни объявлений не влезут в контекст, медиану и разброс агент считает своим кодом.
  • Разбор цен при выгрузке: «25к», «25 000 ₽», «$300», «торг».
  • Фото объявлений: превью пачкой вместе с выгрузкой, полный альбом по запросу, чтобы агент оценил состояние вещи.
  • Вступление в закрытый чат только с подтверждением. Капчу бота-привратника проходишь ты, не агент.
разовый запрос

Сводка по каналу

«Зайди на этот канал и расскажи, о чём там говорят»

tg_resolve → tg_read_history (brief) → tg_get_message × 5 → tg_get_comments × 5

Что нужно шлюзу

  • Краткий режим ленты: 1-2 строки на пост плюс просмотры, реакции и число комментариев. Месяц постов укладывается в несколько тысяч токенов.
  • Комментарии самых обсуждаемых постов, отсортированные по реакциям.
  • Пометка чужого текста: в комментариях бывают попытки командовать агентом.
постоянная задача

Мониторинг и ответы

«Следи за этим каналом и, когда выходят посты, отвечай на них в комментариях»

tg_rule_set → наблюдатель → запуск агента → tg_reply → согласование в боте

Что нужно шлюзу

  • Наблюдатель за новыми постами, который переживает рестарт и не шлёт дубли.
  • Правило с лимитами: один ответ на пост, N в день, тихие часы.
  • Запуск агента без тебя: claude -p, codex exec или opencode run с токеном только на этот пост.
  • Черновик ответа тебе в Telegram с кнопками, ответ в ветку комментариев.
поручение

Переписка и договорённость

«Напиши такому-то аккаунту и договорись с ним о том-то»

tg_task_start → tg_send → ответ собеседника → tg_task_get → tg_send или вопрос тебе → tg_task_update

Что нужно шлюзу

  • Поручение с памятью: цель, рамки, срок, вся переписка и состояние. Агент между запусками ничего не помнит, помнит шлюз.
  • Список того, что решаешь только ты: деньги, адрес, личные данные, время встречи, выход за рамки. На этом агент останавливается и спрашивает тебя в боте.
  • Твой ответ в боте текстом уходит агенту как указание.
  • Токен только на этот диалог, лимит новых диалогов в день, одно напоминание, если собеседник молчит.

Путь запроса

    Ключевые решения

    Десять решений, от которых зависит, будет ли шлюз одинаково работать в Claude Code, Codex, OpenCode и Hermes и потянет ли он твои кейсы.

    Сессией владеет один процесс

    Демон tg-mcp serve держит MTProto-соединение, очередь и кэш. Агенты подключаются к нему по Streamable HTTP. Для stdio-клиентов есть прокладка tg-mcp stdio: если демон жив, она проксирует, если нет, поднимает ядро у себя под файловой блокировкой.

    helper уже живёт по этому правилу: одна сессия, одна полоса MTProto-вызовов на все воркеры (gramGate), запрет второго клиента в AGENTS.md. Шлюз распространяет его на всех агентов.

    Контракт состоит только из tools

    Resources, prompts и elicitation поддерживаются не везде, а tools понимают все. Схемы плоские: строки, числа, enum, без union и вложенных объектов. Имена tg_* в snake_case, в основном наборе не больше 10-12 инструментов.

    Описания всех инструментов попадают в контекст агента при каждом запуске, поэтому лишние инструменты стоят денег и внимания модели.

    Ядро отдельно от MCP

    Код из channel-scope выносится в пакет tg-core: пул клиентов, лимитер, резолвер, поиск, медиа. Хранилище подключается через порт, по умолчанию SQLite. channel-scope начинает зависеть от того же ядра.

    Сейчас сервисы привязаны к Mongoose-моделям. Для шлюза, который ставится через npx, MongoDB лишняя зависимость.

    По умолчанию только чтение

    Инструменты записи (вступить, реакция, ответ, отправить) живут в отдельном наборе write и выключены. Когда включены, работают в два шага через confirm_token: первый вызов показывает, что будет сделано, второй выполняет. Для мониторинга подтверждается не каждый ответ, а правило целиком: чат, режим, лимиты.

    Двухшаговое подтверждение работает в любом клиенте, в отличие от elicitation.

    Шлюз отдаёт данные, думает агент

    Внутри шлюза нет модели и API-ключей. Сводки, анализ цен и тексты ответов пишет агент. Для постоянных задач шлюз тоже не думает сам, а запускает агента командой из правила: claude -p, codex exec или opencode run.

    Так шлюз не привязан к провайдеру, а в автоматизации работает тот же агент с теми же навыками, что и в разговоре с тобой.

    Большие объёмы уходят в файл

    Для аналитики по сотням объявлений tg_export возвращает путь к JSONL, число строк и пять примеров. Считает агент своим кодом. Картинки тоже ложатся файлами на диск, а агент открывает только те, что нужны. Для сводок наоборот: краткий режим ленты, чтобы месяц постов поместился в контекст.

    Все четыре клиента умеют запускать код. Тысяча объявлений в контексте стоит дорого, и модель считает по ним хуже, чем pandas.

    Пишет тот, кто подключён

    Шлюз не выбирает личность сам. Подключил отдельный аккаунт агента, пишет он; подключил свой личный, значит, это твоё осознанное решение. В канале, где аккаунт админ, можно писать от имени канала. В правиле и поручении аккаунт указывается явно.

    Ядро channel-scope уже умеет несколько аккаунтов, так что агент и ты можете жить в одном шлюзе, каждый со своей сессией.

    Правило и поручение

    Правило реагирует на событие и забывает его: вышел пост, агент ответил. Поручение помнит цель, рамки и переписку, пока дело не закончится. Наблюдатель, запуск агента и согласование в боте у них общие.

    Агент между запусками ничего не помнит, поэтому состояние поручения хранит шлюз, а не агент.

    Долгое оформляется задачей

    Любой вызов укладывается примерно в 30 секунд. Выгрузка истории, индексация наблюдаемых каналов и обход графа рекомендаций возвращают job_id, прогресс читается через tg_job_status.

    У клиентов есть таймауты на вызов инструмента, и они разные. Если FLOOD_WAIT длиннее бюджета, шлюз сразу отвечает ошибкой с retry_after, а не висит.

    Текст из Telegram считается чужим

    Каждое сообщение в выдаче обёрнуто в явные границы с указанием источника, а инструкции сервера говорят агенту не выполнять команды из этого текста. Личные переписки аккаунта закрыты, пока их не добавят в список.

    Публичные чаты это открытый канал для prompt injection. С включённой записью это уже не теория.

    Что не переносим

    • MCP как HTTP-прокси с логином по паролюmcp/src/index.ts:22 логинится в REST через /api/auth/login и держит cookie. В шлюзе ядро внутри процесса, а к демону ходят с bearer-токеном.
    • JSON.stringify(results, null, 2) в каждом ответеОтступы и все поля подряд съедают контекст агента. Нужен компактный текстовый формат и курсоры.
    • Загрузка всего пайплайна ради одного каналаgetChannelReport, compareChannels, saveChannelReport тянут весь список и ищут канал на клиенте.
    • Прямые вызовы клиента мимо лимитераrecommendationsService, forwardAnalysisService, refreshService, viewsSyncService берут клиента напрямую: весь трафик идёт через первый аккаунт и без учёта FLOOD_WAIT.
    • Глобальный синглтон архиватораarchiveService держит один прогресс на процесс, поэтому идёт одна выгрузка за раз.
    • console.log в сервисахВ stdio-режиме любая строка в stdout ломает JSON-RPC. Логи только в stderr, логгер GramJS туда же или выключить.
    • --dangerously-skip-permissions в харнессе отчётовresearch.ts:173. Терпимо, пока инструменты только читают. С набором write так запускать нельзя.

    Подключение

    Шлюз запускается один раз на машине (или на VPS рядом с агентом), дальше каждый клиент добавляет его одной записью в конфиг.

    Команда tg-mcp install <клиент> будет печатать эти фрагменты сама. Синтаксис конфигов клиентов записан по памяти, перед выпуском пакета его стоит сверить с текущей документацией каждого клиента.

    Риски

    От самых дорогих к самым мелким.

    • высокий
      Ограничение или бан аккаунта.

      Автоматизация через user-аккаунт Telegram терпит, пока она похожа на человека. Нужен отдельный номер, а не основной аккаунт, консервативные лимиты из rateLimiter (60 в минуту, 500 мс между запросами) и никаких массовых вступлений и рассылок.

    • высокий
      Автоответы в чужих каналах.

      Регулярные комментарии под каждым постом чужого канала быстро выглядят как спам: админы банят, антиспам Telegram ограничивает аккаунт. По умолчанию режим draft с согласованием, один ответ на пост, дневной лимит, тихие часы и случайная задержка перед ответом. Режим auto разумен в своих каналах.

    • высокий
      Сообщения незнакомым людям.

      Это самое рискованное для аккаунта: после жалоб Telegram оставляет только переписку со взаимными контактами (PEER_FLOOD). Лимит новых диалогов в день, никаких рассылок, агент представляется помощником.

    • высокий
      Обязательства от твоего имени.

      В переговорах агент может пообещать лишнее. Всё, что касается денег, адресов, личных данных, времени встречи и выхода за рамки, решаешь ты: поручение переходит в «вопрос тебе». Переводов денег агент не делает вообще.

    • высокий
      Одна сессия в нескольких процессах.

      Если Claude Code и Codex одновременно запустят свои копии с одной сессией, Telegram может её сбросить (AUTH_KEY_DUPLICATED). Лечится демоном-владельцем и блокировкой в stdio-режиме. По той же причине шлюзу нужна своя сессия, отдельная от прод-сессии helper.

    • средний
      Охват поиска.

      messages.searchGlobal ищет по чатам, где состоит аккаунт, а не по всему Telegram. Корпус задаётся подписками аккаунта и локальным индексом. Поиск по хэштегам работает по публичным постам. Полнотекстовый поиск по всем публичным постам Telegram открыл позже и в урезанном виде (Premium, дневная квота); поддержку нужного слоя API в GramJS надо проверить отдельно.

    • средний
      Prompt injection из чатов.

      Комментарии и посты пишут посторонние люди. Защита: обёртка недоверенного контента, отдельный набор write, двухшаговое подтверждение, аудит.

    • средний
      Личные переписки.

      Агент видит всё, что видит аккаунт. Личные чаты закрыты по умолчанию и открываются только списком.

    • средний
      Вступление в закрытые чаты.

      В барахолках часто стоят боты-привратники с капчей. Агент её не проходит: шлюз останавливается и просит вступить вручную. Массовые вступления сами по себе повод для ограничений.

    • средний
      Персональные данные продавцов.

      В объявлениях есть имена и телефоны. В выгрузке авторы хэшируются, телефоны маскируются, пока их явно не попросили.

    • средний
      Пропущенные посты.

      После переподключения GramJS может потерять часть обновлений. Наблюдатель всегда дочитывает историю с последнего виденного id, а не полагается только на события.

    • низкий
      Слишком большие ответы.

      Клиенты режут или предупреждают о больших ответах инструментов (в Claude Code это настраивается через MAX_MCP_OUTPUT_TOKENS). Лимит на символы в сообщении, 20 результатов по умолчанию, курсоры.

    • средний
      Зависший запрос GramJS.

      При сбоях сети вызов может не вернуться никогда, и без дедлайна встаёт весь воркер: helper так простоял 9 дней в августе. Дедлайн на каждый вызов, watchdog и перезапуск процесса супервизором берём из helper.

    • низкий
      Логи в stdout.

      GramJS по умолчанию пишет свои сообщения в консоль. В stdio-режиме это ломает протокол, поэтому логгер отключается или уводится в stderr.

    План

    Код живёт в монорепо channel-scope: packages/tg-core (вынесенное ядро) и packages/tg-mcp (шлюз). Старый packages/mcp остаётся инструментом CRM-пайплайна.

    1. Вынести ядро

      Из channel-scope: clientManager, rateLimiter, telegramUtils, processMediaClient. Из helper: gramGate, refreshShared (дедлайны, FLOOD_WAIT, классификация ошибок), gramStartup и gramFatalRecovery, discussion.ts и чтение треда из commentsRefresher, reactionKey, chatId. Всё в tg-core, Mongoose заменяется портом хранилища. Тесты переезжают вместе с кодом: у helper они покрывают как раз комментарии, гейт и старт.

    2. Чтение и аналитика: кейсы 1 и 2

      Демон с HTTP, stdio-прокладка, tg-mcp login, SQLite, скоупы, аудит, обёртка контента. Краткий режим ленты, темы форумов, выгрузка с разбором цен. Готово, когда промпты про барахолку и сводку канала одинаково отрабатывают в claude -p, codex exec и opencode run (по образцу харнесса из research.ts).

      tg_status · tg_resolve · tg_search_messages · tg_search_chat · tg_read_history · tg_get_message · tg_get_comments · tg_list_topics · tg_export · tg_get_media

    3. Мониторинг: кейс 3

      Наблюдатель с дочиткой по minId, правила с лимитами, запуск агента по шаблону команды, согласование через отдельного бота, ответ в комментарии. Только режим draft. Сначала на своём канале.

      tg_rule_set · tg_rules · tg_inbox · tg_reply · tg_join

    4. Поручения: кейс 4

      Поручения с состоянием и перепиской, наблюдатель за личными чатами, вопросы и отчёты в боте, ответ текстом как указание агенту, лимит новых диалогов. Сначала только режим draft.

      tg_task_start · tg_task_get · tg_task_update · tg_tasks · tg_send

    5. Расширения

      Поиск каналов через лимитер, локальный FTS-индекс, аналитика из channel-scope, режим auto для своих каналов, несколько аккаунтов через pickActiveClientId, мост к архивам channel-scope, команда install под каждый клиент.

      tg_find_channels · tg_similar_channels · tg_list_dialogs · tg_forward_sources · tg_watch · tg_job_status · tg_local_search · tg_react · tg_channel_stats
