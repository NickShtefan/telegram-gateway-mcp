# Риски

От самых дорогих к мелким.

## Высокие

**Ограничение или бан аккаунта.** Автоматизация через user-аккаунт Telegram терпит, пока похожа на человека. Нужен отдельный номер, консервативные лимиты (в лимитере channel-scope 60 запросов в минуту и 500 мс между запросами), никаких массовых вступлений и рассылок. Кроме ограничений бывает заморозка аккаунта (только чтение, апелляция через @SpamBot); её видно в `help.getAppConfig` (`freeze_since_date`, `freeze_until_date`), и `tg_status` с `doctor` должны о ней сообщать.

**Сообщения незнакомым людям.** Самое рискованное действие для аккаунта: после жалоб Telegram оставляет только переписку со взаимными контактами (`PEER_FLOOD`). Лимит новых диалогов в день, никаких рассылок, агент представляется помощником.

**Обязательства от имени владельца.** В переговорах агент может пообещать лишнее. Деньги, адреса, личные данные, время встречи и выход за рамки решает владелец: поручение переходит в «вопрос тебе». Переводов денег агент не делает вообще.

**Автоответы в чужих каналах.** Регулярные комментарии под каждым постом чужого канала быстро выглядят как спам: админы банят, антиспам Telegram ограничивает аккаунт. Только `draft`: каждый ответ ждёт подтверждения владельца, один ответ на пост, дневной лимит, тихие часы, случайная задержка. `auto` разумен в своих каналах.

**Правила Telegram про ИИ.** Content Licensing and AI Scraping (telegram.org/tos/content-licensing) запрещает использовать данные платформы для работы ИИ без явного согласия всех участников конкретного чата. Формально под запрет попадает любой шлюз, который отдаёт модели чужие каналы и чаты, включая все аналоги из [prior-art.md](prior-art.md). Для Business-ботов отдельно запрещена передача сообщений в сторонние API без разрешения пользователя. Это риск, который владелец принимает сознательно; снижают его личное использование, отсутствие массового сбора и работа только с теми чатами, которые владелец назвал сам.

**Одна сессия в нескольких процессах.** Два процесса на одной сессии дают `AUTH_KEY_DUPLICATED`, и Telegram её сбрасывает. Лечится демоном-владельцем и блокировкой в stdio-режиме. По той же причине у шлюза своя сессия, отдельная от прод-сессии helper.

**Кража сессии агентом.** Агенты работают с shell под тем же пользователем macOS (`nick`), что и демон. Агент, которого увели через prompt injection, может прочитать файл сессии вместе с ключом шифрования и получить аккаунт целиком. Защита принята: демон работает под отдельным пользователем macOS, файлы сессий и ключ агентам недоступны (решение 17).

## Средние

**Охват поиска.** `messages.searchGlobal` ищет по чатам, где состоит аккаунт, а не по всему Telegram. Поиск по хэштегам (`channels.searchPosts`) работает по публичным постам. Полнотекстовый поиск по всем публичным постам Telegram открыл позже и в урезанном виде (Premium, дневная квота); поддержку нужного слоя API в GramJS надо проверить отдельно.

**Prompt injection из чатов и от собеседников.** Защита: обёртка чужого контента, отдельный набор `write`, запись в два шага с подтверждением через `tg_confirm` (решение 23), токены на один пост или один диалог, аудит.

**Личные переписки.** Агент видит всё, что видит аккаунт. Личные чаты закрыты по умолчанию, открывает их владелец поштучно. Поручение открывает диалог только агенту этого поручения и только с его первого сообщения.

**Разделение пользователей.** Токены и файлы обоих пользователей лежат под одним пользователем macOS. Шлюз разделяет доступ по токену, но агент с shell может прочитать чужой токен из конфига Claude Code. Это защита от ошибок, а не от злого умысла.

**Вступление в закрытые чаты.** В барахолках часто стоят боты-привратники с капчей. Агент её не проходит: шлюз останавливается и просит владельца вступить вручную.

**Персональные данные.** В объявлениях имена и телефоны продавцов. В выгрузке авторы хэшируются, телефоны маскируются, пока их явно не попросили. Локальный индекс (`tg_index`) хранит тексты проиндексированных чатов и имена авторов в базе шлюза: она лежит у пользователя демона и агентам недоступна, индекс удаляется командой или вместе с аккаунтом.

**Пропущенные события.** После переподключения GramJS может потерять часть обновлений. Наблюдатель всегда дочитывает историю с последнего виденного id.

**Зависший запрос GramJS.** При сбоях сети вызов может не вернуться никогда. Без дедлайна встаёт весь воркер: helper так простоял с 3 по 12 августа 2026. Дедлайн на каждый вызов, watchdog и перезапуск процесса супервизором берём из helper.

**Платные действия.** Premium-пользователи могут брать Stars за сообщения от незнакомых (`ALLOW_PAYMENT_REQUIRED`), глобальный поиск по публичным постам сверх квоты тоже стоит Stars (`allow_paid_stars`). Шлюз никогда не выставляет `allow_paid_stars` сам: поручение переходит в «вопрос тебе», поиск возвращает ошибку.

**Подтверждение без посредника.** Бота согласований нет (решение 23): запись подтверждает агент владельца вызовом `tg_confirm` после его согласия. Шлюз не видит, было ли согласие на самом деле, поэтому агент, которого увели через prompt injection в разговоре, технически может подтвердить сам. Защита: в клиенте `tg_confirm` оставлен в режиме «спрашивать разрешение», запуск без человека подтверждать не может вообще, лимиты шлюза (один ответ на пост, дневные пределы, закрытые личные чаты) от агента не зависят.

## Низкие

**Слишком большие ответы.** Клиенты режут или предупреждают о больших ответах инструментов (в Claude Code настраивается через `MAX_MCP_OUTPUT_TOKENS`). Лимит на символы в сообщении, 20 результатов по умолчанию, курсоры.

**Картинки дорогие.** Каждая стоит модели сотни или тысячи токенов. По умолчанию превью.

**Логи в stdout.** GramJS по умолчанию пишет в консоль; в stdio-режиме это ломает протокол. Логгер отключается или уводится в stderr.
