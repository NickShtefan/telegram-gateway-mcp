# Owner setup worker and protected handoff

The service-side owner worker and installed POSIX/Windows human terminal entries are implemented and tested with synthetic input. Its authorized coordinator must supply real OS/service identity attestation, paused-agent human terminal conditions, supervisor stop/freeze and exclusive setup/session ownership. No administrative MCP/HTTP endpoint is exposed. Real owner qualification remains unfinished; source and synthetic checks must not be presented as live installation proof.

`src/setup/owner.ts` validates owner-selected setup/account/user identifiers and explicit replacement/rotation flags. Authorization precedes prompts/storage effects. The worker runs only while the setup lease and stopped-daemon/session ownership are held. It asks for own API credentials, phone, code and 2FA through hidden direct-human prompts; server-provided password hints are not forwarded to public progress. Authentication logging is silent. Existing completed sessions, bearer hashes and scope rules are preserved on repeat runs unless the owner explicitly requests replacement/rotation.

Authentication RPC calls are intercepted into `core/tg.ts` and the account limiter/deadline boundary. Private auth calls retain teleproto control exceptions (including the password-required branch) until the outer authentication result is classified. Nested migration/configuration calls use deliberate reentrant ownership with sibling serialization, rate accounting and the enclosing deadline; they never enqueue behind their own parent RPC. Auth operations have no automatic FLOOD_WAIT retry/code resend. A stalled connection or client cleanup terminates the worker instead of continuing with a potentially live client and releasing session ownership. The coordinator may resume supervision only after it proves the worker has exited. Canceled input cannot return a session even if a library callback returns normally. POSIX prompts settle on EOF, Ctrl-C or worker-exit abort signals. Windows hidden-key input checks service termination and the overall deadline while waiting, with Ctrl-C/Ctrl-Z cancellation, so a dead worker cannot leave the owner coordinator indefinitely awaiting input.

`ApiCredentialFile` writes the private service `.env` atomically and preserves unrelated settings. Reads reject links, nonregular/hard-linked/oversized/foreign-readable state. Windows file ACL attestation is mandatory rather than treating mode bits as ACL proof. No other project credentials are discovered or copied. Actual secrets never enter arguments, environment handoffs, logs, screenshots or agent-managed inputs.

New gateway users receive token hashes; raw tokens are sealed into a service-private pending handoff record using the session secret. Failed/repeated client setup retains this record without rotation. Authorized adapter handoff can decrypt it internally and validates the current user hash; no public result or stdout includes the token. Receipt acknowledgement removes the pending value only for the matching token hash. An existing user whose pending credential is no longer available requires a direct existing-client credential route or explicit owner-approved rotation, not silently issuing a new token.

The returned owner result contains only setup UUID, phase and a fixed error code. It never includes account identity, API hash, phone, code, 2FA hint/password, session, encryption key or bearer token. A setup UUID is correlation only. Passing an internal authorization callback in a unit test is not proof of real owner authorization or service isolation.

POSIX supervisor controls operate on reconstructed fixed profiles with a controlled environment. macOS disable/bootout and Linux stop plus runtime Restart=no drop-in prevent automatic competing work; the session lease is the final exclusion boundary. Restore touches only the coordinator's attested runtime definition. The POSIX installed command is `sudo "<prefix>/bin/tg-mcp-owner" setup`. It accepts only this action, reconstructs the fixed profile, attests installed root-owned code and receipts, requires a direct human readiness acknowledgement, and launches a bounded private-pipe worker that drops supplementary groups/gid/uid before touching private state. The worker acquires both setup and session leases before opening storage. The coordinator restores supervision only after an OS-confirmed worker exit. Repeat setup retains the installation setup UUID and does not rotate tokens or replace a completed session.

On Windows the installed `application/dist/setup/owner-windows.ps1 -SourceSha <installed SHA>` runs in an elevated human terminal. It serializes owner operations using an administrator-only file handle, attests the installed profile, freezes recovery and stops the service, then starts an explicit fixed owner-setup mode under the existing virtual service account. A private ACL-protected mailbox carries only closed prompt identifiers, bounded hidden answers and allowlisted results. Answers are deleted on consumption and on coordinator cleanup; the protected nonsecret plan remains for retry. This is an on-demand owner operation, not a background watcher. The helper checks the actual virtual-account SID and private file/ancestor ACLs. Setup child stdout/stderr are never written to logs. Service stop waits for the worker to exit before returning; recovery is restored only after confirmed stop. Real Windows execution remains a qualification gate.

Tests cover authorized ordering, private input, encrypted session/token persistence, repeated invocation/scopes, cancellation, no unauthorized mutation, pending retry/acknowledgement, explicit rotation and corrupted pending records. Existing core login regressions include cancellation despite a normal library return and required fatal termination on stuck cleanup. All real test sessions are created separately on their machine, using the owner-controlled account/channel selected for qualification; every real write retains preview/consent.

Stage 6 adds the [original-user launcher and client adapters](client-adapters.md). The default installed command now starts unelevated and requests the scoped elevation internally; the lower-level stage 5 administrator entry remains internal. New API credentials are written only after successful login, so failed/canceled initial authorization does not cache a mistyped pair. Per-user handoff correlation and validation permit separate users while retaining prior pending data for retry. Real platform/provider qualification is still pending.
