# Authenticated installation artifacts

The terminal artifact foundation is implemented. It does not install/activate a service or authorize production elevation by itself. The independently reviewed initial owner verifier, protected platform provisioning, production signing-key onboarding, remote public acquisition and real no-Node environment qualification remain separate release gates.

## Bundle contract

A candidate contains `manifest.tsv`, a detached RSA-3072/SHA-256 PKCS#1 signature (`manifest.sig`), and a DER X.509 certificate (`signer.der`) used only as a public-key container. It is not a CA/OS publisher certificate. Authenticate its exact SHA-256 fingerprint through an independent owner channel before using its public key. A fingerprint printed by the builder or supplied alongside the download is diagnostic, not an independent trust anchor.

The version-1 manifest is ASCII with fixed ordered metadata and exactly six artifact records: standalone Node, installer entry, manifest/archive helpers, canonical application archive and Node license. It binds version, source SHA, platform, architecture, exact Node version, sizes and hashes. Unknown/repeated records, filenames, fields, controls, unsupported Node branches and oversized data are rejected. Windows uses `node.exe`; POSIX uses `node`.

`src/install/manifest.ts` checks the pinned DER fingerprint, RSA key type/size, detached signature and exact caller-approved release/platform identity. Artifact byte checks bind size and SHA-256. The standalone installer rechecks the signature/policy and every candidate file, checks its actual Node version, validates the complete application archive and returns safe metadata with `installed: false`. It does not provision, issue tokens, log into Telegram or change client configuration.

## Runtime provenance

`scripts/install/runtime-catalog.json` pins official Node 24.21.0 and 22.23.3 assets by version/platform/architecture. These were captured October 8, 2026 from official release checksums, whose detached signatures were verified with the Node release keyring at commit `481637f813e912c4aa3622d7964ab426c97b8e8d` (keyring SHA-256 and verified signer are recorded in the catalog). The verification used a separate temporary GPG home, not the user's private keyring. A valid signature is interpreted against this pinned official keyring, not GPG's unrelated personal web of trust.

The build-time `fetch-runtime.mjs` downloads only the exact catalog URL over HTTPS, refuses redirects, bounds data and checks the pinned whole-asset digest before any system archive reader or executable sees it. It extracts only the Node executable and license from the authenticated upstream archive. It executes `--version` only for a host-matching runtime. Different-target binaries remain unexecuted. The acquisition receipt is not authority: the normal bundle builder independently compares the complete upstream asset digest to the checked-in catalog and re-extracts the actual Node/license bytes before signing.

Node 24's official binaries require macOS 13.5+, while Node 22 supports earlier macOS. Select Node 22 for the accepted macOS 13.0-13.4 target; choose the tested Node 24 elsewhere subject to platform qualification. Sources: [Node 24 platform requirements](https://github.com/nodejs/node/blob/v24.x/BUILDING.md), [Node 22 platform requirements](https://github.com/nodejs/node/blob/v22.x/BUILDING.md), [Node 24.21.0 release](https://nodejs.org/en/blog/release/v24.21.0). The minimum supported Node 22.13 and all declared OS/client environments still require the final matrix; acquiring a checksum-verified binary does not prove compatibility.

## Application archive and private staging

`src/install/archive.ts` produces and reads a deliberately narrow canonical USTAR gzip format. Only regular files are accepted. It rejects traversal/absolute paths, backslashes/ADS/Windows-reserved names, duplicate/case-colliding paths, file/directory conflicts, links/devices/extension records, unsafe modes (execution is allowlisted only for the authenticated native lease helper), bad checksums, nonzero padding and hidden/truncated archives. Compressed/decompressed/per-file/count budgets are enforced. The full archive is validated before any extraction write.

Extraction requires an already-existing empty owned directory and uses exclusive no-follow file creation, preserving owner execution for the allowlisted lease helper only. It never adopts or overwrites an installation. POSIX ownership/mode checks are implemented; Windows ACL attestation and protected staging belong to the Windows adapter. A partial candidate is disposable staging, not completed service state.

The POSIX bootstrap uses fixed system tools to verify the pinned certificate/signature, strict manifest, copied artifact hashes and target identity before invoking the staged Node. A fixed system-Perl descriptor reader enforces regular-file/no-follow/nonblocking open, byte budgets and a deadline on snapshots before hashing/parsing; source replacement cannot turn the copy into an unbounded FIFO or growing-file read. System Perl/OpenSSL availability is a bootstrap capability gate, not a Node/npm prerequisite. It clears Node/shell injection variables, uses a private temporary candidate and never uses Node/npm from PATH. macOS runtime minimums are checked before execution. `verify` validates and removes the candidate; `prepare` validates/extracts and retains a private candidate with `installed: false`. It is not a self-authenticating downloaded root installer: the initial owner trust/elevation path must acquire verified code independently in protected staging before any production privileged invocation. Agent-writable source copies and hashes from the same untrusted channel are insufficient.

The PowerShell bootstrap currently performs non-activating pinned-signature/target/file verification using Windows/.NET facilities without Node. It does not execute Node/helpers from its source folder or change service/UAC settings. PowerShell/native Windows execution and the full protected runtime handoff remain Windows platform gates. No execution-policy or OS trust bypass is a supported installation instruction.

## Building and checking candidates

Build tooling needs Node/npm; POSIX runtime acquisition/build fixtures use system tar/unzip/OpenSSL and signature provenance uses GPG. These are builder tools, not target Node/npm prerequisites. The builder reads a protected private signing-key file and never copies it into the bundle or prints it. Normal signed candidates require a clean exact Git HEAD, 0.2.0 ESM application metadata and authenticated runtime material. `--fixture-runtime` explicitly produces a development fixture with synthetic key/metadata and a distinct builder outcome; it is not a publishable qualification result.

Source builds on macOS compile a tiny universal `flock` helper with deployment target 13.0. The earlier system `lockf` FD-only CLI is newer than the accepted minimum macOS, so installed consumers use this bundled helper and need no compiler. It only locks inherited descriptor 3, leaving the parent's open-file description as the owner, and never unlinks state. Kernel/legacy recovery tests run against it. Apple source comparison: [older lockf implementation](https://github.com/apple-oss-distributions/shell_cmds/blob/8ddef153ec48fd196b3707317aa1f11b22ce44ec/lockf/lockf.c), [FD-mode implementation](https://github.com/apple-oss-distributions/shell_cmds/blob/14a2692995de90c2fde0c3c1e639a8c7d9e2312d/lockf/lockf.c). This build target is not a substitute for live macOS 13/Intel qualification.

Current automated proof covers signature/policy mismatch, tampering, malformed manifests, archive threats and a POSIX entry with PATH restricted to system tools. Signing keys are generated only in temporary fixtures; real credentials/sessions are never test inputs. Exact upstream Node versions have been exercised on the development Mac, separately from fresh-environment/service/client proof. Native Windows/Linux/minimum macOS and actual installation remain unverified until their recorded qualification steps.
