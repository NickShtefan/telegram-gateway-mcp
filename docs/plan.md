Всё проверено тестами на двойниках Telegram и Bot API (996 тестов на основном Mac и на лабораторной машине под Node 22), ошибки Telegram в тестах создаются настоящими классами GramJS. Код прошёл два независимых ревью (безопасность и корректность), находки исправлены (решение 22). На живом Telegram шлюз ещё не запускался.

Что осталось руками владельца:

1. Тестовый номер и `TG_API_ID`, `TG_API_HASH`.
2. Установка на лабораторной машине под sudo: копия установщика под root и запуск с sha коммита ([deploy.md](deploy.md)).
3. Бот согласований через BotFather, его токен в `.env` демона.
4. Запустить runner под своим пользователем ([connect.md](connect.md)).
5. Провайдер моделей для OpenCode на лабораторной машине, если нужен прогон в третьем клиенте.

После этого: прогон сценариев из [scenarios.md](scenarios.md) на живом Telegram и правка того, что разойдётся с тестами.

Фазы идут по кейсам: каждая заканчивается тем, что конкретный кейс работает в трёх клиентах. Для фазы 0 всё решено: демон работает на лабораторной машине, номер для тестов даёт владелец (решения 12-14 в [decisions.md](decisions.md)).

## Предлагаемая структура кода

Один npm-пакет `telegram-gateway-mcp` (приватный, команда `tg-mcp`), внутри слои из [architecture.md](architecture.md):

```
tg-mcp/
├── src/
│   ├── core/         # пул клиентов, сессии, лимитер + гейт, страж зависаний, резолвер, кэши
│   ├── services/     # поиск, чтение, комментарии, темы форумов, выгрузка, медиа, действия
│   ├── policy/       # скоупы, шлюз записи, обёртка чужого контента, аудит
│   ├── automation/   # наблюдатель, правила, поручения, запуск агента, согласование, Business-бот, входящие
│   ├── mcp/          # реестр инструментов, форматтер, курсоры, задачи, рецепты
│   ├── transport/    # Streamable HTTP, stdio-прокладка
│   ├── storage/      # порт хранилища и реализация на SQLite
│   └── cli/          # login, serve, stdio, runner, doctor, install
├── docs/
├── reference/        # снимок исходников, только чтение
└── scripts/
```

`core` и `services` не импортируют ничего из `mcp` и `transport`.

## 0. Каркас и ядро

- `package.json` (`telegram-gateway-mcp`, `"private": true`, команда `tg-mcp`), `tsconfig`, vitest, линтер, структура папок. Цель Node 22: на лабораторной машине 22.22.
- Перенести из `reference/` с тестами:
  - channel-scope: `clientManager` (шифрование сессий, вход, пул), `rateLimiter`, `telegramUtils`, `processMediaClient`, `processReactions`;
  - helper: `gramGate`, `refreshShared` (дедлайны, FLOOD_WAIT, классификация ошибок), `gramStartup`, `gramFatalRecovery`, `reactionKey`, `chatId`, `env`.
- Заменить Mongoose-модели портом хранилища, сделать SQLite-реализацию для сессий и кэша сущностей. Схема сразу с пользователями, аккаунтами и доступом (решение 16).
- Лимитер: дедлайн внутри полосы, кап FLOOD_WAIT, бюджет ожидания с `retry_after`, приоритет интерактивных вызовов над фоновыми.
- CLI `tg-mcp login --account <имя>` (вход с кодом и 2FA, шифрованная сессия; каждый входит в свой аккаунт сам), `tg-mcp user add` (пользователь и его токен) и `tg-mcp doctor`.

Готово, когда: тесты ядра проходят, `login` и `doctor` работают на тестовом аккаунте, в зависимостях нет Mongo.

## 1. Чтение и аналитика: кейсы 1 и 2

- Демон `tg-mcp serve` со Streamable HTTP и bearer-токеном, stdio-прокладка с блокировкой. Установка на лабораторную машину: отдельный пользователь macOS (создаёт владелец), LaunchDaemon, общая папка для выгрузок и картинок (решение 17). Токен на пользователя, параметр `account`, доступ только к своим и общим аккаунтам.
- Политики: скоупы (личные чаты закрыты), обёртка чужого контента, аудит.
- Сервисы: резолвер ссылок t.me, поиск (глобальный, в чате, хэштеги), чтение с режимом `brief`, комментарии (из helper `discussion.ts` и `commentsRefresher.ts`, без записи в базу), темы форумов, выгрузка с разбором цен и превью фото, медиа.
- Форматтер, курсоры, ошибки с `retry_after`, задачи для долгой выгрузки.

Инструменты: `tg_status`, `tg_resolve`, `tg_search_messages`, `tg_search_chat`, `tg_read_history`, `tg_get_message`, `tg_get_comments`, `tg_list_topics`, `tg_export`, `tg_get_media`.

Готово, когда: промпты кейсов 1 и 2 из [scenarios.md](scenarios.md) одинаково отрабатывают в `claude -p`, `codex exec` и `opencode run`.

## 2. Мониторинг: кейс 3

- Наблюдатель: обновления GramJS плюс сверка по расписанию (лестницы из helper `ageTiers.ts`, `commentsAgeTiers.ts`), последний виденный id в SQLite. Список чатов ведёт агент через `tg_watch`.
- Правила с лимитами, запуск агента через `tg-mcp runner` у каждого пользователя (решение 17) с токеном на один пост, отдельный бот согласований, `tg_reply` с `send_as`.
- Только режим `draft`. Первые проверки на своём канале. Согласование приходит тому пользователю, чьё это правило.

Инструменты: `tg_watch`, `tg_rule_set`, `tg_rules`, `tg_inbox`, `tg_reply`, `tg_join`.

## 3. Поручения: кейс 4

- Поручения с состоянием и перепиской, наблюдатель за личными чатами, вопросы и отчёты в боте, ответ владельца текстом как указание агенту.
- Лимит новых диалогов в день, одно напоминание, токен на один диалог.
- Режим `via=business` (решение 13): Business-бот принимает `business_message` и отвечает через `business_connection_id`, первое сообщение отправляет владелец по ссылке от бота, окно ответа 24 часа.
- Только режим `draft`.

Инструменты: `tg_task_start`, `tg_task_get`, `tg_task_update`, `tg_tasks`, `tg_send`.

## 4. Расширения

- Поиск каналов через лимитер, локальный FTS-индекс, аналитика из channel-scope.
- Режим `auto` для своих каналов.
- Опрос публичных каналов любым свободным аккаунтом пользователя через `pickActiveClientId`.
- Мост к архивам helper и channel-scope в MongoDB.
- Команда `tg-mcp install <клиент>`, рецепты как MCP prompts и markdown-файл для AGENTS.md и skills.

Инструменты: `tg_find_channels`, `tg_similar_channels`, `tg_list_dialogs`, `tg_forward_sources`, `tg_index`, `tg_job_status`, `tg_local_search`, `tg_react`, `tg_channel_stats`.
