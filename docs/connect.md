# Подключение и конфиги

Шлюз запускается один раз, каждый клиент добавляет его одной записью. Установка на лабораторную машину: [deploy.md](deploy.md). Ниже считается, что демон слушает `http://127.0.0.1:7777/mcp`, а команды лежат в `/opt/telegram-gateway-mcp/bin`.

Что проверено на лабораторной машине 1 октября 2026 с живым Telegram: Claude Code (подключение, `claude mcp list`), Hermes (`hermes mcp add`, `hermes mcp test`), Codex (полный сценарий «сводка по каналу»). OpenCode: только подключение, для прогона нужен провайдер моделей.

`npx tg-mcp` не использовать: в npm под этим именем чужой пакет (решение 14).

## Пользователи и аккаунты

Пользователи шлюза, их токены и доступ к аккаунтам лежат в базе демона и управляются командой владельца (решение 16). Файла конфигурации для этого нет.

```bash
sudo /opt/telegram-gateway-mcp/bin/tg-mcp-admin user add nick --account agent
```

Команда печатает токен один раз. В базе хранится только его хэш.

```bash
sudo /opt/telegram-gateway-mcp/bin/tg-mcp-admin user list
```

```bash
sudo /opt/telegram-gateway-mcp/bin/tg-mcp-admin account grant agent partner
```

## Claude Code

Сервер добавляется в профиль пользователя. Токен при этом записывается в конфиг профиля (`.claude.json`, права 600).

```bash
claude mcp add --scope user --transport http tg-gateway http://127.0.0.1:7777/mcp \
  --header "Authorization: Bearer $(cat ~/.config/tg-mcp/token)"
```

- Имя сервера любое. На лабораторной машине это `tg-gateway`, а не `telegram`: имя `telegram` уже носит плагин бота-моста, и агент путал бы их. Инструменты тогда называются `mcp__tg-gateway__tg_status` и так далее.
- Если профилей несколько, перед командой укажи нужный: `CLAUDE_CONFIG_DIR=/Users/nick/.claude claude mcp add ...`. Второй пользователь делает то же в своём профиле со своим токеном.
- Проверка: `claude mcp list` должен показать `tg-gateway ... Connected`. Уже открытая сессия увидит сервер после перезапуска.
- Разрешения. Чтобы агент не спрашивал подтверждение на каждое чтение, в `settings.json` профиля можно разрешить сервер целиком, а подтверждение записи оставить с вопросом:

```json
{
  "permissions": {
    "allow": ["mcp__tg-gateway"],
    "ask": ["mcp__tg-gateway__tg_confirm"]
  }
}
```

Файл для запуска без интерфейса (`claude -p --mcp-config`), он же нужен runner:

```json
{
  "mcpServers": {
    "telegram": {
      "type": "http",
      "url": "http://127.0.0.1:7777/mcp",
      "headers": { "Authorization": "Bearer ${TG_MCP_TOKEN}" }
    }
  }
}
```

## Codex

Запись в `~/.codex/config.toml`. Таймаут вызова стоит поднять: выгрузка ждёт до 20 секунд, прежде чем вернуть `job_id`.

```toml
[mcp_servers.telegram]
url = "http://127.0.0.1:7777/mcp"
bearer_token_env_var = "TG_MCP_TOKEN"
tool_timeout_sec = 90
```

Разовый запуск без правки конфига (проверено):

```bash
TG_MCP_TOKEN=... codex exec --skip-git-repo-check \
  -c 'mcp_servers.telegram.url="http://127.0.0.1:7777/mcp"' \
  -c 'mcp_servers.telegram.bearer_token_env_var="TG_MCP_TOKEN"' \
  "Call tg_status and tell me which accounts I have."
```

## OpenCode

Запись в `opencode.json` проекта или в глобальный конфиг (подключение проверено командой `opencode mcp list`).

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "telegram": {
      "type": "remote",
      "url": "http://127.0.0.1:7777/mcp",
      "headers": { "Authorization": "Bearer {env:TG_MCP_TOKEN}" }
    }
  }
}
```

Для `opencode run` на лабораторной машине нужен провайдер моделей: сейчас их нет, а бесплатные модели в неинтерактивном режиме не работают.

## Hermes

Hermes хранит токен в своём `~/.hermes/.env`, а в `config.yaml` ставит ссылку на него. Имя переменной он строит из имени сервера: для `tg-gateway` это `MCP_TG_GATEWAY_API_KEY`.

```bash
printf '\nMCP_TG_GATEWAY_API_KEY=%s\n' "$(cat ~/.config/tg-mcp/token)" >> ~/.hermes/.env
```

```bash
hermes mcp add tg-gateway --url http://127.0.0.1:7777/mcp --auth header
```

Команда спросит, нужна ли авторизация (да), найдёт токен в `.env`, покажет инструменты и предложит включить все. В `config.yaml` получится:

```yaml
mcp_servers:
  tg-gateway:
    url: http://127.0.0.1:7777/mcp
    headers:
      Authorization: Bearer ${MCP_TG_GATEWAY_API_KEY}
    enabled: true
```

Проверка: `hermes mcp test tg-gateway`. Инструменты появятся в новой сессии Hermes.

## Любой клиент со stdio

Прокладка проксирует в демон и сама сессий не открывает. Токен в `TG_MCP_TOKEN`.

```json
{
  "command": "/opt/telegram-gateway-mcp/bin/tg-mcp",
  "args": ["stdio"],
  "env": { "TG_MCP_TOKEN": "<токен пользователя>" }
}
```

## Наборы инструментов и запись

В `.env` демона (`/var/tgmcp/.tg-mcp/.env`):

```
TG_MCP_TOOLSETS=core,write
```

- `core`: чтение и поиск. Включён по умолчанию.
- `write`: ответы, сообщения, вступление. Всегда в два шага.
- `automate`: наблюдение, входящие, правила, поручения. Нужен, только если агент должен работать, пока тебя нет.

Отдельного бота нет (решение 23). Запись выглядит так: ты просишь агента ответить под постом, он вызывает `tg_reply` и показывает тебе предпросмотр, ты говоришь «да», он вызывает `tg_confirm`, и шлюз отправляет сообщение.

Шлюз не видит, спросил ли агент тебя на самом деле. Поэтому в Claude Code не добавляй `mcp__telegram__tg_confirm` в список разрешённых без вопроса: пусть клиент спрашивает разрешение на каждый вызов. Остальные инструменты шлюза можно разрешить целиком, они ничего не отправляют. Для агента, которого запускает runner, это не нужно: `tg_confirm` ему шлюз не даёт вовсе.

## Runner: запуск агента по правилам и поручениям

Когда срабатывает правило или отвечает собеседник в поручении, агента запускает `tg-mcp runner`. Он работает под твоим пользователем macOS, у каждого пользователя шлюза свой (решение 17).

```bash
TG_MCP_TOKEN=<токен пользователя> /opt/telegram-gateway-mcp/bin/tg-mcp runner \
  --agent 'claude -p {prompt} --mcp-config ~/tg-mcp/agent.mcp.json --strict-mcp-config --allowedTools "mcp__telegram__*"'
```

Как это устроено:

- runner спрашивает у демона задание раз в 5 секунд, запускает команду и сообщает исход. По одному заданию за раз, таймаут 3 минуты.
- `{prompt}` подставляется одним аргументом, без оболочки. Поэтому переменные вроде `$HOME` в команде не раскрываются; `~/` в начале аргумента runner раскрывает сам.
- Если агент вышел, но оставил фоновый процесс, runner считает запуск законченным через две секунды после выхода агента.
- Агент получает в `TG_MCP_TOKEN` не твой токен, а токен запуска. По нему шлюз даёт только один пост и один ответ (правило) или один диалог (поручение). Поэтому в `agent.mcp.json` должен стоять `${TG_MCP_TOKEN}`, как в примере выше.
- Для Codex команда такая: `codex exec --skip-git-repo-check -c 'mcp_servers.telegram.url="http://127.0.0.1:7777/mcp"' -c 'mcp_servers.telegram.bearer_token_env_var="TG_MCP_TOKEN"' {prompt}`.
- Второй пользователь запускает свой runner со своим токеном и `CLAUDE_CONFIG_DIR` своего профиля.

Чтобы runner работал постоянно, его ставят как LaunchAgent пользователя: [deploy.md](deploy.md).

## Как ты узнаёшь о черновиках и вопросах

Шлюз сам тебе не пишет. О том, что случилось без тебя (правило подготовило ответ, собеседник в поручении о чём-то спросил, поручение закрылось), знает твой агент:

- `tg_status` показывает, сколько запросов и вопросов ждёт тебя;
- `tg_inbox` отдаёт события после курсора;
- `tg_confirm action=list` показывает черновики с текстом.

Чтобы не спрашивать агента вручную, дай ему расписание: в Hermes это cron-задача «проверь tg_inbox и напиши мне, если есть что-то новое», в Claude Code то же самое через `/loop` или запланированную задачу. Писать тебе агент будет своим обычным каналом (тем же ботом-мостом, через который вы уже общаетесь).

## Правило (кейс 3)

Правило готовит агент через `tg_rule_set`. Оно включается после `tg_confirm`, то есть после твоего согласия в разговоре с агентом. Аргументы плоские:

```json
{
  "id": "reply-new-posts",
  "chat": "@channel",
  "prompt": "Прочитай пост, картинку к нему и комментарии. Напиши короткий ответ по существу.",
  "keywords": ["ставка", "рынок"],
  "skip_ads": true,
  "per_day": 5,
  "quiet_hours": "20:00-06:00",
  "send_as": "account"
}
```

- Время тихих часов в UTC.
- Перед запуском агента случайная пауза 60-300 секунд.
- Один ответ на пост с аккаунта, чьё бы правило ни сработало (решение 18).
- Режим только `draft`: агент, запущенный по правилу, сам ничего отправить не может. Его черновик ждёт тебя: твой агент видит его в `tg_inbox` и в `tg_confirm action=list`, показывает тебе и подтверждает после твоего «да». Черновик живёт 12 часов.
- Выключить правило: `tg_rule_set` с `enabled: false`, согласие не нужно.

## Поручение (кейс 4)

Аргументы `tg_task_start`:

```json
{
  "peer": "@seller_username",
  "goal": "Купить велосипед из объявления t.me/baraholka/123",
  "limits": "До 15 000 ₽. Самовывоз в субботу или воскресенье днём.",
  "ask_me_before": ["over_limits", "money_transfer", "address", "personal_data", "meeting_time"],
  "first_message": "Здравствуйте! Пишу как помощник покупателя по объявлению о велосипеде. Он ещё продаётся?",
  "deadline": "3d",
  "max_messages": 20,
  "reminder_after": "24h",
  "via": "account"
}
```

- Поручение целиком и первое сообщение агент показывает тебе в предпросмотре. Первое сообщение можно переписать: скажи агенту свой текст, он передаст его в `tg_confirm`.
- Каждое следующее сообщение собеседнику тоже ждёт твоего подтверждения. Вопросы поручения к тебе и отчёт приходят во входящие (`tg_inbox`); твой ответ агент передаёт через `tg_task_update state=answer`.
- `money_transfer` добавляется всегда: деньги решаешь только ты.
- Способа `via=business` больше нет (решение 23). Чтобы переписка шла от твоего имени, подключи к шлюзу свой личный аккаунт и укажи его в `account`.
